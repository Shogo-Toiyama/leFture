# Account deletion is too slow (2026-11-23)

## Problem
- `/auth/delete-account` often takes longer than the app's 30 s timeout. The server keeps going and finishes the deletion, but the app shows a timeout error and stays signed in. A retry then gets 401 `user_not_found`.

## Cause (measured)
`run_test.py` runs the production deletion functions with random UUIDs (every DELETE matches 0 rows; `auth.users` is not touched) and times every PostgREST / R2 call. Measured from the developer PC, not Cloud Run.

- Every call is sequential and takes about 100 ms (DB) or about 420 ms (R2 `delete_prefix`).
- Per lecture: 11 DB calls + 1 R2 call, about 1.4-1.7 s. User-level part: 22 calls, about 2.6 s.
- With production lecture counts (25 users with lectures, median 7, max 84): over 30 s from about 16-20 lectures; 4-6 users would time out; the largest about 120-150 s.

## Change
- `_hard_delete_lectures_bulk`: delete all of the user's lectures table by table with `in_()` (100 ids per call), in the same table order as `_hard_delete_lecture`. The per-lecture R2 deletes are dropped because the final `delete_prefix("{uid}/")` already removes `{uid}/{lecture_id}/`.
- `_hard_delete_user_data` uses it, and also deletes `store_subscription_sync_state` (it has no FK to `auth.users`, so a row was left behind).
- App: when the request times out or fails, check with GoTrue whether the user still exists (`user_not_found`); if it is gone, treat the deletion as done (sign out, wipe local data).

## Result (same method, 0-row deletes, median of 3)
| Lectures | Before (projected) | After (projected) | Sequential calls for lectures |
|---|---|---|---|
| 1 | 4.1 s | 3.7 s | 10 |
| 7 (median user) | 12.6 s | 3.7 s | 10 |
| 84 (largest user) | 122.1 s | 4.1 s | 10 |

- Not measured: real row deletion cost, Cloud Run latency, and the GoTrue `auth.users` delete.
- Writes to production: DELETEs that match 0 rows only. Cost: $0.
- `check_leftovers.py <user_id> [lecture_id ...]` (read-only) checks a deleted account for leftover rows, R2 objects and the auth user. On the account deleted earlier today it found the `store_subscription_sync_state` row.
