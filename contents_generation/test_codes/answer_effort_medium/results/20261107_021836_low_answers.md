その「頭の中で1ビットずつどう動くかイメージしきれない」という壁、めちゃくちゃ分かります！文字やコードだけだと、時間のズレがどう累積していくか追いにくいですよね。

でも、今言ってくれた**「受信側は1μs（0.5, 1.5, 2.5…）だと思ってタイマーを回してるけど、送信側は8%遅い」**という前提の捉え方は100点満点です！

この「8%遅い送信側」が送るデータ `10011 11010` を、1ビットずつ手動でシミュレーションしてみると、一気に視界が開けます。一緒に表を組み立てるように追ってみましょう。

---

### 前提の整理
* **受信側の予測（Nominal）：** 本来の1ビットは $T = 1\mu\text{s}$。最初のサンプリングは $0.5\mu\text{s}$ 後。
* **送信側の現実（Sender）：** 受信側より **8% 遅い**。つまり、送信側にとっての1ビットの実際の長さは、
  $1\mu\text{s} \times 1.08 = \mathbf{1.08\mu\text{s}}$ になります。
* **送るデータ：** `1 0 0 1 1 1 1 0 1 0`

### 1ビットずつ追いかけてみよう

時間を $t = 0$ のプリアンブル完了（最初の基準）からスタートします。

#### 1. 最初のビット（`1`）
* 送信側は、自分にとっての $1.08\mu\text{s}$ かけて最初の `1` を送ります。
* 受信側は nominal に従って、**$t = 0.5\mu\text{s}$** のタイミングで最初のサンプリングをします。
* ここではまだトランジション（0から1、1から0の変化）がないので、`lag = 0` のまま。次の予測時間 $P$ は $P + T + \text{lag} = 0 + 1 + 0 = 1.0\mu\text{s}$ に設定され、タイマーは次の $0.5\mu\text{s}$（合計 $1.5\mu\text{s}$）を待ちます。

#### 2. 次のビット（ここから `1` → `0` への変化がある場合）
データは `1 0 0 1 1...` なので、2ビット目の `0` に切り替わるときに**トランジション（電圧の変化）**が起きます。
* 送信側が実際にその変化を起こす時間は、8%遅れているので、$1.08\mu\text{s}$ の地点です。
* 受信側が予測していたタイマーの期限は $1.5\mu\text{s}$ あたり。
* このとき、**「実際の変化のタイミング（$A$）」と「予測していたタイミング（$P$）」にズレ（$\text{lag} = A - P$）が生じます！**

コードのこの部分：
```text
If Transition is detected at actual time A
lag = A - P // 実際の時間 - 予測の時間
...
P = P + T + lag // 次の予測を今回のズレ（lag）で修正する
```
受信側は、このトランジションをキャッチした瞬間に「おっと、思ってたより（あるいは思っていなかったより）ちょっとズレてるな？」と `lag` を計算し、次の予測 $P$ やタイマーの長さをその分だけパッと書き換える（補正する）わけです。
