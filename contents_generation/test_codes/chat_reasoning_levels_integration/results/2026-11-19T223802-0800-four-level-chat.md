# Four-level chat routing and reasoning progress

The candidate uses the committed v3 rubric verbatim. The previously tested clock-recovery example remains acceptable at medium. The historical replay got the reference values right at medium on both runs. This run did not widen the rubric or try to elicit a live high classification.

## Dry runs

- Checked the production router template, enum, legacy boolean normalization, malformed decisions, and blocked/crisis decisions. Ran seven stream cases across all four levels and 20 attachment cases covering new, mentioned, already visible, and already scheduled attachments.
- Reconstructed three developer-owned turns through the existing Supabase replay builders. The router and provider were mocked. The candidate's medium answer request was built with 20 messages from the recorded calculation turn.
- Intercepted all four final Anthropic HTTP request bodies using LiteLLM 1.104.2. The none body set `thinking.type=disabled`. Low, medium, and high each sent the corresponding `output_config.effort` with summarized adaptive thinking. The mocks checked that a missing thought, a late summary, and a stalled summary allow the first answer delta through.
- The existing progress unit suite passed 4/4 and the English/Japanese web rendering suite passed 14/14. The Flutter conversation view suite passed 65/65. The integration dry-run passed with Python 3.11 and 3.14. All three historical router prompts still reproduce with their enum schema.
- Provider tokens and cost were zero for the dry runs.

All three received their expected levels. The Japanese answers used a warm, informal tutoring tone. The scope explanation distinguished local and global variables correctly, and the calculation checked that 90 gives a weighted total of 84. Neither eligible turn in this final run published a custom label before text began. They started with the generic thinking status. The app records first thought, first published label, and first answer text times so that the publish rate can be measured by level after deployment.

The first synthetic run exposed LiteLLM omitting Haiku's effort when its model map lacked the capability. In that run the router selected all three expected levels and the scope case published one label at 2,795 ms, before its 5,091 ms TTFT. The adapter now registers the supported capability, and the final HTTP dry-run verifies that all four request bodies carry the intended settings.

The first synthetic run's estimated provider cost was $0.00685015. The final run was $0.00366134. Total reported provider usage cost was $0.01051149. Canceled calls may have unreported tokens. Production routing accuracy, end-to-end latency, and the frequency of high selections and progress labels remain to be measured.
