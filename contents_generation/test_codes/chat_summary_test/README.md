# チャット要約の評価用データ

チャットボットのロードマップ(`docs/chatbot_context_and_retrieval_roadmap.md`)ステップ2「スレッド要約」の
品質を確かめるための、手で書いた会話の台本。**まだ評価は実行していない。** ユーザーが台本の中身を見て
GOを出してから、要約パイプラインに通して評価を始める(設計の2-13)。

## ファイル

```
build_conversations.py   会話データ本体(往復・probe)。ここが正本。編集する時はこのファイルを直す
conversations/*.json     ↑を実行して書き出したもの(生成物。直接編集しない)
```

再生成: `python build_conversations.py`

## 会話は5本

| ファイル | 言語 | 往復数 | 主に見ること |
|---|---|---|---|
| `learning_deep_dive_ja` | ja | 28 | 学習の深掘り。**block1とblock2の両方**をテスト |
| `topic_switching_en` | en | 20 | 話題が何度も変わる。block1のみ |
| `preference_ja` | ja | 27 | 好みの指定。**2回の畳みをまたいでヘッダーに残るか** |
| `emotional_arc_en` | en | 20 | 気持ちが変わっていく相談。block1 + 口調の質のチェック |
| `code_reference_ja` | ja | 18 | 前に出したコードの中身を参照。block1 |

## たたみ方のスケジュール(設計2-3を実際の往復数に当てはめた結果)

- 未要約の往復が**15**になったら、古い**10**往復を1段目のブロック(block1)に畳む(残り5往復)
- その後raw(直近5往復)が育って再び15往復になったら、**25**往復目で2回目の畳み(block2 = round11-20)
- この規模(20〜28往復)では、block1が10個たまって2段目に畳まれる(設計2-4)ところまでは起きない。それは
  100往復規模になるので、必要になったら別途、手書きではなくプログラムで長い会話を作って確かめる

つまり実際に起きるのは:
```
round 1〜10  → round15で block1 に畳まれる
round 11〜20 → round25で block2 に畳まれる
round 21〜   → まだraw(このテストの規模では畳まれない)
```

`build_conversations.py`のテストコードでこのシミュレーションを実行し、各probeの
`requires_info_from_round`が宣言どおりの層(block1/block2)に入るかを機械的に検算済み。

## probeの読み方

各会話ファイルの`probes`は、「会話の自然な流れの中にある質問を、そのまま評価用の質問として使う」形にしてある。
別途、評価専用の不自然な質問は作っていない。

- `history_through_round`: この往復までを文脈として使う(=ここまでが要約パイプラインを通る対象)
- `probe_round`: この往復の`user`発言を、新しい質問として(生の履歴 / 要約後の文脈の)2通りで実際にモデルに投げる
- この往復の`assistant`発言は、**執筆時点では全履歴があった前提で書いた「正解の目安」**。要約後の回答がこれと
  同じ要点を含められているかを比べる
- `key_facts_must_include` / `key_facts_must_not_include`: 比較のときに機械的にもチェックできるよう、
  正解の目安から要点だけ抜き出したもの
- `qualitative_checks`: 文字列一致では確認しづらい、人が読んで判断するポイント(口調・感情の流れなど)

## 例: `preference_ja`が一番厳しいテストになっている理由

round4で「数式は最小限、たとえ話だけで」と一度だけ指定される。これは設計の「①会話の前提(ヘッダー)」に
入る想定の情報。round15で1回目、round25で2回目の畳みが起きた後、round26で本人がこの指定そのものを
聞き返す。**ヘッダーが2回の畳みをまたいで正しく引き継がれるか**を確認する、今回のセットで一番厳しいテスト。

## この後の流れ

1. **(今ここ)** ユーザーがこの5本の中身を確認し、シナリオ・自然さ・probeの妥当性にGOを出す
2. 要約パイプライン(GPT-6 Luna、設計2-7)を実装する
3. 各会話を実際に要約パイプラインに通し、各probeについて
   「生の全履歴で答えた場合」と「要約+直近の原文で答えた場合」を並べたレポートを作る
4. レポートを見て、閾値(往復数)やプロンプトを調整する
