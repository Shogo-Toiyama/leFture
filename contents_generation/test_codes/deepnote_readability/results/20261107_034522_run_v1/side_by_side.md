# Topic 1 — PRODUCTION (baseline)

## 🔍 DNSの階層構造

DNSは木のような階層になっていて、上の段ほど広い範囲の情報を知っています。一番上にあるルートサーバーは、トップレベルドメイン（TLD）のDNSサーバーを知っています。トップレベルドメインとは、.com、.edu、.govのような末尾の部分のことです。⟦s000012-s000014⟧

各段は、自分の下にある名前の情報を持っています。たとえば .edu のサーバーは、UCLA.edu のように .edu の下に登録されたドメインを知っています。UCLA は、cs.ucla のような自分の配下のゾーンを知っています。⟦s000015-s000017⟧

サブドメイン（subdomain）は、ドメインの下にさらに作られる名前です。たとえば support.uber.com がこれにあたります。ただし、サブドメインは必須ではなく、作るかどうかは管理者が決められます。⟦s000018⟧

下の段ほど、サーバーの数は多くなります。上の段にあるサーバーより、下の段にあるサーバーのほうが多いという関係です。⟦s000029-s000030⟧

### 階層と実際のサーバーは一致しない

階層の区切りは「管理の境界」を表していますが、それぞれの区切りが別々のサーバーに置かれるとは限りません。UCLA が一台のDNSサーバーで複数の階層をまとめて担当することもあります。また、好きなように分けて配置することもできます。⟦s000019-s000024⟧

> 要するに、階層は「誰が何を管理しているか」を示す設計図であり、物理的なサーバーの配置そのものではありません。⟦s000019-s000024⟧

なお、ゾーン（zone）とドメイン（domain）の細かい違いも話題に出ましたが、試験には出ないと明言されています。必要なら参考程度に留めてください。⟦s000025-s000028⟧

## ⚙️ 再帰的リゾルバーによる名前解決の流れ

クライアント（たとえばノートパソコン）が google.com や ucla.edu の情報を知りたいとき、まず **ローカルリゾルバー** に問い合わせます。名前解決は1回の通信では終わらないため、リゾルバーが代わりに何段階もの問い合わせを行います。⟦s000033-s000041⟧

この仕組みを **再帰的DNSリゾルバー（recursive DNS resolver）** と呼びます。リゾルバーは、クライアントの代わりにDNSサーバーを順番にたどって、最終的な答えを返します。⟦s000037-s000041⟧

```
クライアント → ローカルリゾルバー（再帰的）
                 ├─ ① ルートに問い合わせ → ".edu のサーバーはここ"
                 ├─ ② .edu に問い合わせ  → "ucla.edu のサーバーはここ"
                 └─ ③ ucla.edu に問い合わせ → 答え（IPアドレス）
```

（上の図は理解のための例です。）

流れの要点は次のとおりです。

- リゾルバーは必ず最初にルートへ問い合わせます。⟦s000041-s000042⟧
- ルートは、次に問い合わせる先（たとえば .edu のサーバー）を教えてくれます。⟦s000045-s000047⟧
- .edu のサーバーは、UCLA のサーバーを教えてくれます。⟦s000046-s000047⟧
- 問い合わせは、すべてリゾルバー自身が行います。ルートや他のDNSサーバーが、代わりに全部の検索をしてくれるわけではありません。⟦s000047-s000049⟧

ルートは世界中に多数存在します。ひとつのルートが止まっても困らないように、リゾルバーは複数のルートのうちのどれかに問い合わせる仕組みになっています。⟦s000042-s000045⟧

## 🧭 ルートヒントとキャッシュ

リゾルバーは、最初からどこに問い合わせればいいか知っているわけではありません。起動時に持っているのが **ルートヒント（root hints）** で、アクセスできるルートの IPアドレスの一覧です。⟦s000050-s000052⟧

ルートヒントがあれば、リゾルバーは動き始め、得た情報を **キャッシュ（cache）** として保存できます。キャッシュとは、一度調べた答えを手元に覚えておくことです。⟦s000052-s000053⟧

キャッシュがないと、たとえば .edu の場所を知りたいだけなのに、毎回ルートへ問い合わせることになります。すでに一度調べたことは覚えておけば、同じ問い合わせを毎回最初から繰り返さずに済みます。⟦s000054-s000056⟧

## 📡 フォワーダー：家庭やISPでの役割分担

家庭のルーターが、すべての再帰問い合わせを自分で処理するのは現実的ではありません。問い合わせの数が多く、キャッシュを大量に持つ必要があり、近所の人も似た問い合わせをしていることが多いからです。⟦s000059-s000064⟧

そこで家庭では **DNSフォワーダー（DNS forwarder）** を使うのが一般的です。フォワーダーは、受け取った問い合わせを上位のリゾルバーへ転送する中継役です。⟦s000065-s000067⟧

例として、家庭の端末が名前解決を頼んだとします。

1. 端末は、家庭内のフォワーダーに問い合わせます。
2. フォワーダーは、上位のリゾルバー（たとえば ISP のリゾルバーや 1.1.1.1 のような公開リゾルバー）へ転送します。⟦s000067-s000071⟧
3. 上位のリゾルバーが、実際の再帰的な名前解決を行います。

フォワーダーは、家庭内の問い合わせ結果もキャッシュできます。よく見る cnn.com の結果を保存しておけば、次に同じ家庭の人が使うときに早く答えられます。⟦s000072-s000074⟧

同じ ISP の中にある別の家庭も、上位リゾルバーのキャッシュを共有できるため、近所全体で恩恵を受けます。⟦s000071-s000072⟧

### 🛡️ フォワーダーで広告を止める例

PiHole（パイホール）は、フォワーダーとして家庭のネットワークに置けるオープンソースのツールです。広告ネットワークのドメイン名の一覧を持っており、その名前への問い合わせを受け取ると破棄します。⟦s000076-s000080⟧

たとえばウェブサイトが adnetwork33.com から広告を読み込もうとすると、フォワーダーはその問い合わせを捨てます。広告は取得できず、ページは広告なしで表示されます。⟦s000080-s000084⟧

## 🏠 ipconfig /all で見る家庭のネットワーク

ipconfig /all コマンドで、自分の端末が DHCP から受け取った設定を確認できます。家庭の Wi-Fi で得られる情報には、IPアドレス、デフォルトゲートウェイ、DNSサーバーなどが含まれます。⟦s000088-s000091⟧

### プライベートIPアドレスとNAT

家庭の Wi-Fi で割り当てられるアドレスは、192.168.x.x のような **プライベートIPアドレス（private IP address）** です。インターネット上の誰もが勝手に使えるアドレスではなく、家庭内などの限られた範囲で使うための番号です。⟦s000097-s000101⟧

プライベートIPアドレスの範囲には、192.168.x.x のほかに、172.16〜の範囲や 10.で始まる範囲もあります。⟦s000099-s000101, s000176-s000177⟧

ルーターの背後にいる端末は、**NAT（ネットワークアドレス変換）** を通して外部と通信しています。外の世界から見える本当のIPアドレスは、ルーターが持つものです。端末のプライベートIPアドレスは、家庭の中だけで意味を持ちます。⟦s000102-s000104⟧

NATが生まれた背景として、IPアドレスは32ビットしかなく、世界の機器の数に対して足りないという問題があります。そのため、多くの機器が1つのルーターのIPアドレスを共有する仕組みが必要になりました。⟦s000168-s000175⟧

NATでは、ルーターが外向きの通信を仲介します。内側からの問い合わせを、ルーター自身のIPアドレスと一意なポート番号に置き換えて送り、返事を元の端末へ戻します。⟦s000180-s000186⟧

### DHCPサーバー、ルーター、DNSを一体化する家庭

家庭では、DHCPサーバーとルーターとDNSサーバーが同じ機器にまとめられていることが多いです。⟦s000113-s000120⟧

ただし、一台がルーティング、DHCP、DNSリゾルバーのすべてを担うのは重すぎます。そのため、家庭のDNSサーバーは多くの場合フォワーダーです。⟦s000120-s000126⟧

公開IPアドレスを直接持っている場合は、その機器がDNSリゾルバーとして動いていることが多いです。そうでなければ、そもそもその機器に問い合わせる理由がないからです。⟦s000127-s000129⟧

## 🏫 UCLAの場合との違い

大学のWi-Fiでは、家庭とは構成が大きく異なります。UCLAには、自分たちで管理するDNSサーバーが複数あり、その中の2つが設定に現れました。⟦s000132-s000138⟧

- **DNSサーバー:** 大学が自前で持つDNSリゾルバーを使います。大学の規模に合わせて複数用意されています。⟦s000134-s000138⟧
- **DHCPサーバー:** 問い合わせが非常に多いため、家庭とは別の専用の基盤が使われます。⟦s000139-s000140⟧
- **IPv6とIPv4:** デフォルトゲートウェイにはIPv6アドレスが設定されており、IPv4にしか対応していない端末のためにIPv4アドレスも用意されています。⟦s000142-s000145⟧
- **プライベートIPとNAT:** 172.で始まるプライベートIPアドレスが使われており、大学でもNATの内側にいることになります。⟦s000145-s000146⟧

昔は、大学が十分なIPアドレスを持っていたため、接続するとIPアドレスをそのまま配っていました。今はそうではなく、非公開の内部ネットワークの内側に置かれるようになっています。⟦s000147-s000149⟧

## 🧮 サブネットマスクで送り先を判断する

サブネットマスク（subnet mask）は、IPアドレスのうち「ネットワーク部分」を判定するための値です。端末は、これを使って宛先が近くにあるかどうかを判断します。⟦s000151-s000156⟧

判断の結果によって、送り方が2通りに分かれます。

- **同じローカルネットワーク内の宛先:** データリンク層（レイヤー2）で直接送ります。⟦s000157-s000158⟧
- **別のネットワークの宛先:** IPを使い、ルーターを経由して送ります。⟦s000155-s000156, s000161-s000162⟧

判定は、IPアドレスとサブネットマスクをビットごとに演算して、ネットワーク部分が一致するかどうかで行います。講義では AND で説明され、比較の細部は XOR とも表現されましたが、基本は「ネットワーク部分が同じか」を見る点にあります。⟦s000159-s000160⟧

### 💡 数値の例で確認する

サブネットマスクが 255.255.255.0 の端末を考えます。この場合、先頭の3つの数字がネットワーク部分になります。

```
端末のIP:    192.168.1.23    → ネットワーク部分 192.168.1.0
宛先A:       192.168.1.50    → ネットワーク部分 192.168.1.0  （同じ → 直接送る）
宛先B:       192.168.2.10    → ネットワーク部分 192.168.2.0  （違う → ルーター経由）
```

（この例は理解のための仮の数値です。）

宛先Aは、先頭3つの数字が一致するため、同じネットワーク内にあると判断されます。宛先Bは一致しないため、ルーターを経由して送られます。

## 🎯 Key Takeaway

- DNSは階層で管理されますが、階層と物理サーバーは一致するとは限りません。⟦s000019-s000024⟧
- 再帰的リゾルバーは、ルートから順にたどって名前解決を完了させ、キャッシュで同じ問い合わせを繰り返さないようにします。⟦s000041-s000042, s000052-s000056⟧
- 家庭やISPでは、フォワーダーが問い合わせを上位のリゾルバーへ転送し、キャッシュを共有します。⟦s000065-s000074⟧
- 家庭の端末は、プライベートIPアドレスとNATを使ってインターネットと通信し、DHCPで受け取った設定（IPアドレス、ゲートウェイ、DNS）を使います。⟦s000088-s000104⟧
- サブネットマスクは、宛先が同じネットワーク内か、ルーター経由が必要かを判断する役割を持ちます。⟦s000155-s000162⟧

# Topic 1 — v1

# 1. DNS階層とネットワーク設定

DNS（ドメインネームシステム）(Domain Name System) は、ドメイン名を対応する情報に変換する仕組みで、ルート、トップレベルドメイン、個々のドメインへと情報をたどる階層になっています。再帰的DNSリゾルバー (recursive DNS resolver) がこの階層を代わりにたどり、ホームルーターのようなフォワーダー (DNS forwarder) は問い合わせを上位へ中継します。さらに、サブネットマスク (subnet mask) を使うと、通信相手が同じネットワーク内にいるか、ルーター経由が必要かを判断できます。

## 🌳 DNSの階層構造

DNSは、レベルごとに知っている情報が違う多数のサーバーで構成されています。一番上にあるのがルートサーバーで、トップレベルドメイン (top-level domain) のサーバーを知っています。トップレベルドメインとは、`.com`、`.edu`、`.gov` などの末尾の部分のことです。⟦s000012-s000014⟧

階層を下るほど、より細かい情報を持つサーバーになります。例えば `.edu` のサーバーは、`ucla.edu` のように `.edu` の下に登録されたドメインをすべて知っています。そして `ucla.edu` のサーバーは、その下のサブゾーン（`cs.ucla` のような部分）を知っています。⟦s000015-s000017⟧

- **サブドメイン**: 例えば `support.uber.com` のように、ドメインの下に作る部分です。ただし必須ではなく、作るかどうかは組織が決めます。⟦s000018⟧
- **階層の境界と物理的な配置**: 階層の区切り（ドットの位置）は管理の境界を表しますが、それぞれが別々のサーバーに置かれるとは限りません。UCLAのように、複数の階層を1台のサーバーにまとめることも、自由に分割することもできます。⟦s000019-s000024⟧
- **サーバーの数**: 階層の下のほうほど、サーバーの数は多くなります。⟦s000029-s000030⟧

> ゾーン (zone) とドメイン (domain) の細かな違いについても触れられていますが、これは発展的な内容で、ここでは深入りしません。⟦s000026-s000028⟧

## 🔁 再帰的DNSリゾルバーの動き方

名前解決の流れは、クライアントから始まります。例えばノートPCで `ucla.edu` を開こうとするとき、PCは直接すべてのサーバーに聞きに行くのではなく、まず**ローカルのリゾルバー**に問い合わせを送ります。名前解決は1回の問い合わせで終わるとは限らないため、代わりに多段の問い合わせをリゾルバーが引き受けるのがポイントです。⟦s000033-s000041⟧

リゾルバーは必ず**ルートから**問い合わせを始めます。ルートはトップレベルドメインのサーバーを教えてくれ、そのサーバーに聞くと目的のドメインのサーバーがわかる、という順にたどっていきます。⟦s000042, s000045-s000047⟧

```
クライアント → ローカルリゾルバー
                  ① ルートに「ucla.edu はどこ？」
                  ② ルートが .edu のサーバーを教える
                  ③ .edu のサーバーが ucla.edu のサーバーを教える
                  ④ ucla.edu のサーバーが答えを返す
クライアント ← ローカルリゾルバー（答えを受け取る）
```

ここで大事なのは、すべての問い合わせを行っているのは**ローカルの再帰的リゾルバーだけ**だという点です。ルートや他のDNSサーバーが代わりに全部の問い合わせをしてくれるわけではありません。⟦s000048-s000049⟧

また、ルートサーバーは世界中に多数あります。もし1台だけに頼っていて、そのルートが止まってしまうと名前解決ができなくなるためです。⟦s000042-s000045⟧

### 🚀 起動時のルートヒントとキャッシュ

リゾルバーは、どこから問い合わせを始めればよいかを知っている必要があります。そのために持っているのが**ルートヒント (root hints)** で、アクセスできるルートサーバーのIPアドレスの一覧です。⟦s000050-s000052⟧

ルートヒントがあれば、リゾルバーは動き始めて情報を**キャッシュ**（一度得た答えを保存すること）できるようになります。これが大切な理由は、毎回ルートに聞き直すのは無駄だからです。例えば `.edu` のサーバーの場所は一度調べれば覚えておけるので、次からルートに聞く必要はありません。⟦s000053-s000056⟧

## 🏠 フォワーダーという中継役

家庭のルーターが、自分でDNSの再帰的な問い合わせをすべて行うのは現実的ではありません。問い合わせの数が多く、キャッシュも大きく持つ必要があるうえ、近所の人も似たような問い合わせをしていることが多いからです。⟦s000059-s000064⟧

そこで家庭では**フォワーダー (DNS forwarder)** が使われます。フォワーダーは受け取った問い合わせを、上位のリゾルバーへ転送する中継役です。例えば家庭の場合、ISPのリゾルバーや、1.1.1.1のような公開DNSリゾルバーへ転送されます。⟦s000065-s000071⟧

フォワーダーには2つの利点があります。

- **近所全体での共有**: ISPのリゾルバーのキャッシュは近所の人にも役立つため、同じ問い合わせの結果を皆で使えます。⟦s000071-s000072⟧
- **家庭内のキャッシュ**: フォワーダー自身も家庭内の問い合わせ結果を覚えておけます。例えばよく見る `cnn.com` の結果はフォワーダーに残るので、隣の人が別のサイトを見ていても問題ありません。⟦s000072-s000074⟧

### 🛡️ 応用例: PyHole

PyHole（PyHole）は、家庭のネットワークに置くことができるオープンソースのDNSフォワーダーです。家庭のDNS通信をすべてこれに通すように設定します。⟦s000076-s000078⟧

PyHoleは広告ネットワークのドメイン名のリストを持っています。広告ネットワークへの問い合わせを見つけると、その問い合わせを**破棄**します。すると、ウェブサイトは広告を取得できず、広告なしで表示されます。⟦s000078-s000084⟧

## 🔎 ipconfig /all で見るネットワーク設定

`ipconfig /all` を実行すると、PCが受け取った設定を確認できます。講義の例では、無線LANアダプターが家のルーターに接続したときにDHCPから受け取った情報が表示されていました。⟦s000089-s000091⟧

確認できる主な情報は次のとおりです。

- **自分のIPアドレス**: 家のルーターのWi-Fi側で割り当てられたアドレスです。⟦s000091⟧
- **デフォルトゲートウェイ**: 自分のネットワークの外へ出るときの出口になるルーターのアドレスです。⟦s000092⟧
- **DNSサーバー**: 名前解決を任せるリゾルバーです。⟦s000004-s000005⟧

家庭のルーターの例では、デフォルトゲートウェイは `192.168` で始まるアドレスでした。`192.168` で始まるアドレスは私的IPアドレス (private IP address) の範囲で、外部から直接アクセスできる公開アドレスとは区別されます。こうした私的アドレスは、家庭用ルーターでよく使われます。⟦s000097-s000100⟧

家庭では、DHCPサーバー、ルーター、DNSサーバーが1台にまとまっていることが多いです。ルーターにすべての役割を持たせるのは負担が大きいので、この場合のDNSサーバーはフォワーダーであると考えられます。⟦s000113-s000126⟧

逆に、もしルーターが公開IPアドレスを持っていてDNSサーバーとして使われているなら、それは再帰的リゾルバーである可能性が高いです。その機器を使う理由がそこにあるからです。⟦s000127-s000129⟧

### 🏫 大学（UCLA）のネットワーク設定の違い

大学のWi-Fiでも同じ確認をすると、家庭とは違う点がいくつか見えてきます。⟦s000130-s000131⟧

- **DNSサーバーが2台**: 大学が自分で管理するDNSリゾルバーが複数あります。⟦s000132-s000135⟧
- **DHCPサーバーが別物**: 大学は接続数が非常に多いため、DHCPには専用の基盤を使っています。⟦s000139-s000140⟧
- **IPv6とIPv4の併用**: デフォルトゲートウェイにはIPv6アドレスと、IPv4アドレスの両方が示されます。IPv4しか扱えない機器のために、IPv4も用意されています。⟦s000142-s000145⟧
- **私的アドレスの利用**: 大学でも `172` で始まる私的アドレスが使われています。昔は接続するたびに公開IPアドレスが配られていましたが、今はこの私的な領域の内側で動いています。⟦s000146-s000149⟧

## ⚖️ サブネットマスクの役割

サブネットマスクは、IPアドレスのうちどこまでがネットワークの部分かを示す値です。この値を使うと、通信相手が同じローカルネットワーク内にいるのか、ルーターを経由する必要があるのかを判断できます。⟦s000151-s000158⟧

判断の方法は、IPアドレスとサブネットマスクを組み合わせて（一般的にはAND演算で）ネットワーク部分を取り出し、比較するというものです。もし相手と自分のネットワーク部分が同じなら、ローカルで直接通信できます。違えば、ルーターを経由するためにIPの仕組みを使います。⟦s000159-s000162⟧

ここで思い出したいのは、送信方法が2つあることです。ローカル宛てならデータリンク層 (data link layer) で直接通信し、別のネットワーク宛てならIPルーティング (IP routing) を使います。サブネットマスクは、どちらの方法を使うかを決めるための判断材料になります。⟦s000155-s000157⟧

**例（自分で作った計算例）**: 自分のIPアドレスを `192.168.1.20`、サブネットマスクを `255.255.255.0` とします。ネットワーク部分は最初の3つ（`192.168.1`）です。

```
自分:       192.168.1.20  →  ネットワーク部分 192.168.1.0
相手A:      192.168.1.50  →  ネットワーク部分 192.168.1.0  → 同じ → ローカルで直接通信
相手B:      8.8.8.8       →  ネットワーク部分 8.8.8.0     → 違う → ルーター経由（IPルーティング）
```

相手Aは同じ `192.168.1.0` の中にいるので、データリンク層で直接やり取りできます。相手Bは別のネットワークなので、デフォルトゲートウェイのルーターを経由します。

## 🎯 Key Takeaway

- **DNSの階層**: ルート → トップレベルドメイン → ドメイン → サブドメインと、情報をたどる構造になっています。階層は管理の境界を示しますが、必ずしも別のサーバーとは限りません。⟦s000012-s000024⟧
- **再帰的リゾルバー**: クライアントの代わりに、ルートから順に問い合わせを行い、結果をキャッシュします。⟦s000037-s000050, s000053⟧
- **フォワーダー**: 家庭では問い合わせを上位のリゾルバーへ転送し、キャッシュを共有して効率化します。⟦s000065-s000072⟧
- **サブネットマスク**: 相手がローカルか、ルーター経由が必要かを判断する役割を持ちます。⟦s000155-s000162⟧

# Topic 3 — PRODUCTION (baseline)

## 🔍 なぜ共有秘密が必要なのか

まず前提として、**対称鍵暗号**（symmetric key encryption）では、送る側と受け取る側が同じ鍵を持っています。その鍵を使えば、他の人には読めない形で会話できます。⟦s000325-s000327⟧

ここで問題になるのが、最初に鍵をどう共有するかです。遠く離れた相手に鍵を直接送ると、その通信を盗聴されたら鍵ごと相手に知られてしまいます。⟦s000337-s000340⟧

インターネットのような誰でも読める回線の上で、どうやって同じ値を共有するのか。これがこの方式の出発点です。⟦s000346-s000349⟧

## 🎨 絵の具の比喩で考える可換性

仕組みを直感的に理解するために、絵の具の比喩を使います。ここでの重要な性質が、**可換性**（commutativity）です。可換性とは、操作の順番を入れ替えても結果が変わらない性質のことです。⟦s000371-s000372, s000373-s000379⟧

例えば、青の絵の具に黄色を混ぜても、黄色に青を混ぜても、できる色は同じです。ただし、すべての操作が可換なわけではありません。この方式が使えるのは、可換性を持つ操作を選んでいるからです。⟦s000380-s000381⟧

手順は次のようになります。

1. 双方が、公開されている共通の基準色（黄色）を用意します。⟦s000382-s000383⟧
2. それぞれが自分だけの秘密の色を選び、基準色と混ぜます。この混ざった色を公開して送ります。⟦s000383-s000385⟧
3. 相手から受け取った混色に、自分の秘密の色を混ぜます。⟦s000392-s000394⟧
4. 双方が最終的に同じ色になります。どちらの順番で混ぜても同じ結果になるので、両者は同じ共有色を得られます。⟦s000394-s000396⟧

```
共通の基準色: 黄色（Y）
Aliceの秘密色: 青緑（T）  → 公開する混色 Y+T
Bobの秘密色:   オレンジ（O） → 公開する混色 Y+O

Aliceの手順: 受け取った Y+O に T を混ぜる → Y+O+T
Bobの手順:   受け取った Y+T に O を混ぜる → Y+T+O

どちらも同じ色 Y+O+T になる
```

<!-- FIGURE: type="diagram" title="公開混色による共有秘密の作成" description="左右にAliceとBobを置き、中央に公開回線を描く。中央の基準色（黄色）から、Aliceは秘密色Tを混ぜた混色を、Bobは秘密色Oを混ぜた混色を公開回線へ送る。受け取った側は、受け取った混色に自分の秘密色を混ぜる。最後に両者の手元で同じ最終色（Y+O+T）が現れることを矢印で示す。盗聴者は公開された混色だけを見ている点も明示する。" -->

## 🔒 盗聴者が秘密を取り出せない理由

盗聴者は、公開された混色をすべて見ることができます。それでも共有色にたどり着けないように、比喩には三つの性質があります。⟦s000396-s000398⟧

- **不可逆性**（irreversibility）：一度混ぜた色は、元の色に分けられません。⟦s000397-s000398⟧
- **隠れた比率**：盗聴者は公開された二つの混色（黄色とオレンジ、黄色と青緑）を見ても、最終色の正確な比率までは分かりません。最終色は黄色が2、オレンジが1、青緑が1の比率になりますが、その比率は公開情報からは一意に決まりません。⟦s000398-s000405⟧
- **区別不可能性**（distinguishability）：公開された色を見ても、最終色は他のどの色と比べても同じくらい起こりやすい、と見分けられないことが求められます。⟦s000406-s000409⟧

ただし、この絵の具の比喩は直感をつかむための道具です。現実の色では、公開された色から「たぶん暗い色になるはず」と推測できてしまいます。つまり完全にランダムには隠れず、少しずつ手がかりが残ります。⟦s000414-s000423⟧

## 🧮 計算困難性と楕円曲線離散対数仮定

ここで大事なのが、「難しい問題」とは何かです。**計算困難性**（computational hardness）とは、今知られているどのアルゴリズムでも、現実的な時間では解けないという意味です。⟦s000426-s000428⟧

具体的には、**多項式時間**（polynomial time）で解けるアルゴリズムがまだ見つかっていません。知られているのは**指数時間**（exponential time）のアルゴリズムだけで、実際に解こうとすると宇宙の寿命でも終わらないほど時間がかかります。⟦s000428-s000430⟧

ここで「不可逆性」が崩れたら何が起きるかを考えてみます。混色を分けられるなら、盗聴者は公開された色から秘密色を取り出せてしまいます。その場合、双方は同じ色を得られるものの、その色はもう秘密ではありません。⟦s000430-s000439⟧

```
盗聴者が混色を分けられる場合
公開された Y+T と Y+O から
  → Aliceの秘密色 T
  → Bobの秘密色 O
を取り出せる
  → 最終色 Y+O+T を盗聴者も作れてしまう
```

そのため、実際の方式では絵の具の不可逆性の代わりに、別の計算上の仮定を使います。一つは離散対数（discrete log）と呼ばれる仮定で、広く使われています。この授業のプロジェクトでは、**楕円曲線離散対数仮定**（elliptic curve discrete log assumption）を使い、それに基づいてTLS接続を作ります。⟦s000445-s000451⟧

ここで押さえたいのは、安全性は「見えにくさ」ではなく、「効率よく解く方法が知られていない」という仮定に支えられている点です。⟦s000426-s000428, s000445-s000448⟧

## ⚠️ 鍵共有だけでは解決しないこと

ディフィー・ヘルマン鍵共有は、盗聴から秘密を守ることに役立ちます。しかし、通信相手が本当にBobなのかは保証しません。もし通信を乗っ取ったCharlieが、Bobになりすましていたら、鍵共有は成立してしまいます。⟦s000453-s000457⟧

この問題は、公開鍵を認証機関が署名して正しい持ち主と結びつけることで解決する、と次回以降に扱われます。この点は今回の鍵共有の仕組みとは別の問題です。⟦s000458-s000466⟧

## 🎯 Key Takeaway

- ディフィー・ヘルマン鍵共有は、公開回線で共通の秘密値を作る方式です。⟦s000350-s000351, s000361-s000362⟧
- 中心になるのは可換性で、混ぜる順番が違っても同じ結果になることが、双方が同じ共有秘密を得られる理由です。⟦s000371-s000379⟧
- 盗聴者が秘密を取り出せないのは、絵の具の比喩でいえば不可逆性などの性質があるからです。実際の安全性は、楕円曲線離散対数仮定のような計算困難性に基づきます。⟦s000396-s000398, s000447-s000448⟧
- 同じ結果が得られても、その結果が秘密であるとは限りません。秘密性は、その計算が本当に難しいという前提によって保たれます。⟦s000438-s000439, s000426-s000428⟧

# Topic 3 — v1

# 3. ディフィー・ヘルマン鍵共有の仕組み

ディフィー・ヘルマン鍵共有（Diffie-Hellman key exchange）は、盗聴されるかもしれない公開の通信路だけを使って、二人が同じ秘密値を作り出す方法です。その秘密値は後から共通鍵暗号の鍵として使えます。仕組みの土台は、色を混ぜる順番を入れ替えても結果が同じになる可換性（commutativity）と、混ぜた色から元の秘密色を取り出すのが難しい計算困難性（computational hardness）の二つです。

## 🔍 出発点：鍵をどう渡すか

まず、対称鍵暗号（symmetric key encryption）の前提を確認します。対称鍵暗号では、通信する二人が同じ鍵を持っていて、その鍵を使うことで外部の人には読めない形でやり取りできます。⟦s000320, s000325-s000327⟧

ここで問題になるのが、「その共通の鍵をどうやって手に入れるか」です。遠く離れた相手と暗号通信を始めたいのに、鍵そのものを電子メールなどで送ると、途中で誰でも読めてしまいます。⟦s000333-s000340⟧ 鍵を安全に届ける手段がないまま鍵を共有しなければならない、というのがこの問題の核心です。⟦s000343-s000349⟧

> 問題の要点：公開された通信路（インターネットのように誰でも読める場所）で、秘密の値を二人だけが持つようにしたい。

ディフィー・ヘルマン鍵共有は、この一見矛盾する要求に答える仕組みです。⟦s000350-s000351, s000359-s000368⟧

## 🎨 絵の具の比喩で考える

難しい数学に入る前に、絵の具の比喩で直感をつかみましょう。ここでは、黄色を「全員が知っている公開の色」、各自が選ぶ色を「自分だけの秘密の色」とみなします。

### 可換性（commutativity）とは

可換性とは、操作の順番を入れ替えても結果が同じになる性質のことです。青い絵の具に黄色を混ぜても、黄色に青を混ぜても、できあがる色は同じになります。⟦s000372-s000379⟧ 絵の具の混色はこの性質を持っていますが、すべての操作がこの性質を持つわけではない点も押さえておきましょう。⟦s000380-s000381⟧

### 二人の手順

1. 全員が共通の黄色（公開の色）を持つ。⟦s000382⟧
2. Alice と Bob はそれぞれ秘密の色を選ぶ。⟦s000382-s000383⟧
3. 各自が、自分の秘密の色を公開の黄色に混ぜ、できた混合色を相手に送る。⟦s000383-s000385⟧
4. 相手から受け取った混合色に、自分の秘密の色を混ぜ戻す。⟦s000392⟧

例えば、Alice の秘密色をオレンジ、Bob の秘密色を青緑とします。Alice が黄色にオレンジを混ぜた色を送り、Bob が黄色に青緑を混ぜた色を送ります。Alice は受け取った色に自分のオレンジを混ぜ、Bob は受け取った色に自分の青緑を混ぜます。どちらの手元でも「黄色・青緑・オレンジ」の三色が混ざった同じ色になります。⟦s000393-s000395⟧ 混ぜる順番が違っても同じ色になるので、この結果は可換性のおかげです。

<!-- FIGURE: type="diagram" title="絵の具による鍵共有の流れ" description="中央に公開の黄色を置く。Alice側は秘密のオレンジを黄色に混ぜて混合色Aを作り、Bob側は秘密の青緑を黄色に混ぜて混合色Bを作る。AとBは公開通信路を通って相手に送られる。Alice側は受け取ったBに自分のオレンジを混ぜ、Bob側は受け取ったAに自分の青緑を混ぜ、どちらも同じ最終色（黄色・青緑・オレンジの混合）に到達する。盗聴者は混合色AとBだけを見る。" -->

## 🛡️ 盗聴者が最終色にたどり着けない理由

公開された混合色を見た盗聴者は、秘密の色を推測できるでしょうか。ここで、盗聴者を防ぐ三つの性質が登場します。

- **不可逆性（irreversibility）**：一度混ぜた色は、元の色に分けることができない。⟦s000397-s000398⟧
- **隠れた結果（hidden result）**：送られた二つの混合色を見ても、両方の秘密の混ざり具合を正確に特定することはできない。例えば、「黄色＋オレンジ」と「黄色＋青緑」の二つだけでは、最終色の正確な比率（黄色1：オレンジ1：青緑1）を再現できません。⟦s000398-s000405⟧
- **区別不能性（distinguishability）**：公開された色を観察しても、最終色（例：茶色）が他の色と比べて特別に出やすいとはわからない。⟦s000406-s000409⟧

ただし、絵の具はあくまで比喩です。実際の色では、薄いオレンジと薄い青を見れば「少し暗い色になりそう」と推測できてしまいます。⟦s000416-s000421⟧ 完全にランダムではなく、結果を絞り込めてしまうという点は、比喩の限界として覚えておきましょう。⟦s000421-s000423⟧

## 🧮 「難しい」とは何を意味するのか

ここで、計算困難性（computational hardness）の意味を整理します。ある問題が難しいとは、「その問題を効率よく解くアルゴリズムがまだ知られていない」ことを指します。⟦s000426-s000428⟧ 知られている解法は、入力の大きさに対して指数的な時間がかかるものばかりで、現実的な時間では終わりません。⟦s000428-s000430⟧

ここで大切なのは、安全性が「見えにくいから」ではなく、「効率的な解法が知られていないという前提（仮定）」に支えられていることです。⟦s000426-s000430⟧ つまり、もし将来だれかが効率的な解法を見つければ、その前提が崩れて安全性も失われます。

### 不可逆性が崩れたらどうなるか

もし混ぜた色を元に戻せたら、何が壊れるでしょうか。二人はそれでも同じ最終色を得られます。計算の規則そのものは変わらないからです。⟦s000437-s000439⟧ しかし、その色は秘密ではなくなります。盗聴者が「黄色＋青緑」と「黄色＋オレンジ」を分解できれば、二人が最後に作る色（黄色・青緑・オレンジ）を自分でも作れてしまうからです。⟦s000439-s000441⟧

つまり、不可逆性が崩れると、同じ色を得られても「秘密」という目的は失われます。ここから、可換性を保ちつつ、逆算が難しい別の仮定を使う必要が生まれます。⟦s000443-s000445⟧

## 🔐 楕円曲線離散対数仮定への接続

絵の具の比喩は直感には役立ちますが、実際の安全性の根拠としては不十分です。そこで、可換性を保ち、逆算が難しいと仮定される数学的問題を使います。⟦s000445-s000447⟧ その代表例が離散対数（discrete log）で、今回の授業で扱うのは楕円曲線離散対数仮定（elliptic curve discrete log assumption）です。⟦s000447-s000449⟧

この仮定は、「楕円曲線の上で計算された秘密値を、公開された情報から効率よく求めることは難しい」と想定するものです。この考え方を使うと、TLS接続のための鍵共有を、絵の具の例と同じ形で行えます。⟦s000450-s000451⟧

## ⚠️ 注意：鍵共有だけでは「相手が本物か」は分からない

最後に、もう一つの注意点があります。ディフィー・ヘルマンで共有された鍵は、相手が本当に Bob かどうかを保証しません。途中で Charlie が通信を乗っ取り、Bob になりすますことができてしまいます。⟦s000453-s000457⟧

この問題は、公開鍵（public key）を認証局（authority）が署名して保証する仕組みで解決されます。⟦s000463-s000467⟧ 補足すると、秘密の色が秘密鍵（private key）、混合色が公開鍵（public key）に対応する見方がここで示されています。⟦s000459-s000462⟧ 同じ鍵の組み合わせを使えば、暗号化も行えるという点も、後で使う重要な道具です。⟦s000468-s000471⟧

## 🎯 Key Takeaway
