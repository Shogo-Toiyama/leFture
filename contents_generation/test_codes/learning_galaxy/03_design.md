# 設計（ドラフト）

> コンセプト確定・具体化に伴い順次更新。

## 画面構造（3View構成 / LODアーキテクチャ）

ユーザー体験を「マクロ（全体）」「メソ（集合・関係性）」「ミクロ（個別詳細）」の3段階で構成する。

```
[Level 1: 銀河View (マクロ)]
  └─ ピンチイン / ズームでトランジション
[Level 2: 星座・星雲View (メソ)]
  └─ 特定の星を選択 / ズーム
[Level 3: 恒星View (ミクロ)]
```

### 1. Level 1: 銀河View（マクロ）
- **役割**: 見た目の美しさと全体の成長を楽しむ。銀河を回転させて鑑賞する。
- **機能**:
  - 全体Statsの表示（星の総数、銀河の大きさ、記録継続など）。
  - 銀河の自由回転・オートオービット（現行機能の発展）。
- **描画仕様**:
  - 個別星の厳密な座標管理・DB保存は行わない。
  - 現行のプロシージャル生成（`GalaxyConfig`）をベースとし、ユーザーの学習進度に応じてパラメータ（腕の数、星・星雲の色、厚み、輝度など）を変化させて個別性を出す。
  - 星の個別タップは行わない（タップ判定の負荷ゼロ）。

### 2. Level 2: 星座・星雲View（メソ / 仮称）
- **役割**: 意味的なつながりや自分の将来に関連する星の集合（星座・星雲）を鑑賞・確認する。
- **機能**:
  - 自由探索ではなく、**「リスト・表・カルーセル」等から特定の星座や星雲を選択**する。
  - 選択された星座・星雲にカメラがフォーカス（または画面中央にフォーカス展開）。
  - **星雲 (Nebula)**:
    - 意味的に近い星を20〜100個集めた塊。
    - 色やモヤ（ガス）の種類を動的に変え、ユニークな星雲を生成。
    - AIがその星雲に象徴的な名前を付与。
  - **星座 (Constellation)**:
    - 特に強い結びつきを持つ星5〜12個を選出。
    - 2次元平面上に座標配置して星間にエッジを結線。
    - 星座の内容・モチーフに合致した**「ネオン調の星座絵（薄く光る具象線画: ノートPC、ロボット等）」**＋AIによる命名を重畳表示。
    - **生成方式: 3段階パイプライン（後述）** により自動生成。
- **描画仕様**:
  - 銀河内部に入り込んだような背景星の空間を維持しつつ、主役の星座/星雲を際立たせる。

## 星座生成の3段階パイプライン（3-Stage Pipeline）

```
[蓄積された星群 (5〜12個)]
  │
  ▼
【Stage 1: 構想・命名役 (The Visionary)】
  星々のタイトル・物語・ベクトルを読み解き、「〇〇座（例: ノートPC座、探求のフクロウ座）」という
  象徴的な星座名・神話ストーリー・具体的なモチーフ（描くべき具象物）を決定。
  │
  ▼
【Stage 2: 作画役 (The Celestial Artist)】
  決定された具象モチーフに基づき、ネオン調のシンプルなSVG線画（パスデータ）を出力。
  （※ゼロからAIが描く方式と、30〜50種の美麗モチーフテンプレートから選ぶ方式の2通りを検証）
  │
  ▼
【Stage 3: 配置・結線役 (The Astrologer)】
  作画された星座絵の主要頂点（角、ヒンジ、節目、関節など）に、集まった星たち（N個）を順番・重要度順にマッピング。
  骨格となるエッジ（結線）データを生成して星座を完成させる。
  ※個別の星に「左目」などの部位名を厳密に固定する必要はなく、スロットへ自然に割り当てる。
```

### 3. Level 3: 恒星View（ミクロ）
- **役割**: 個々の学び・経験を表す「星そのもの」を詳細に見る。
- **機能**:
  - 一つ一つの星のプロファイル・詳細情報（学んだ内容、日付、元になった講義やチャットの抜粋、気づき）の確認。
  - **星の単位**: 「コンセプト1つ」「経験1つ」「物語1つ」。
  - **星の獲得経路**:
    - ① 講義の分析・生成（ベースラインとして徐々に蓄積）。
    - ② **チャットでの対話・深掘り（最も星が溜まる主力チャネル）**: 復習、新たな気づき、趣味、クラブ活動、アイデア、相談など、「その人らしさ」を言語化した時に高頻度で星が誕生。
    - ③（将来拡張）日記機能（テキスト/音声の一方通行記録＋AIフォローアップ）、音声対話（Gemini Live風）。
- **描画仕様**:
  - 静的なテクスチャ画像の固定配置ではなく、**パラメータ合成によるプロシージャル描画**。
  - パラメータ（大きさ、ベース色、光彩・コロナ、模様・テクスチャパターン、ガスの渦巻き、自転速度など）の組み合わせにより、多数のユニークな星を軽量に表現する。

## 星の数え方と銀河の成長（最終決定 2026-11-22）

> この節が正本。以下の各節の古い数字（1講義50星、1年2万星を集める、係数 k など）は、この節で置き換える。

### 1. 獲得する星は「意味のあるもの」だけを数える
- 星の数は、意味のあるものの数そのもの。数を増やすための水増しや倍率はかけない。
- **講義**: トピックの数だけ星が生まれる（例: 1講義で5個）。キーワード・MicroTopics・Gotcha は、そのトピックの星の中身（小星）として持つが、星の数には数えない。
- **チャット**: 話した分だけ星が生まれる（例: 10往復で15個）。数え方は案2（名前のある星＋根拠の星）を **根拠1つ＝星1個** で使う。実測（開発者本人の内面の会話8スレッド）では1往復あたり約2.5個で、この目安に近い。
- チャットは本人の内面から出る内容なので、講義より多く星が生まれる（講義5個に対しチャット15個、など）。
- 同じアクションで獲得する星の数は、1年を通して一定。後から減ったりしない。

### 2. 銀河の見た目は「集めた星の合計」から式で決める
- 銀河Viewで描画する星は、獲得した星と1対1に対応しない。1つ1つの描画星には紐付けがなく、ただの見た目（図鑑も、描画星と1つずつ対応させない）。
- 描画する星の数・半径・星雲・中心の光・既定の画角は、集めた星の合計を5段階のプリセットの間で対数補間して決める（`user_interface/lib/application/galaxy/galaxy_growth.dart`）。
  - 序盤は速く、後半はゆるやかに育つ。中くらいの銀河（描画5,000個、「銀河の形に見える」段階）には開始1か月以内、大きい銀河（描画20,000個）には約1年、巨大な銀河（描画30,000個）には2〜3年で届く。
  - 5段階の値: 生まれたて（500個・半径0.4・中心0.1・星雲0・光0.1。2026-11-22 光を0.2→0.1に修正）/ 小さい（1,000個・中心25%・半径0.5・中心0.15・星雲5・光0.2）/ 中くらい（5,000個・中心20%・半径0.7・中心0.2・星雲20・光0.4）/ 大きい（20,000個・中心15%・半径1.0・中心0.2・星雲40・光1.0。2026-11-22 星雲を100→40に修正）/ 巨大（30,000個・中心10%・半径1.6・中心0.3・星雲80・光1.5。2026-11-22 星雲を150→80に修正）。
  - 小さい銀河ほど星1個を大きく・明るく描く（星の大きさの倍率 starScale: 生まれたて3.0 / 小さい2.2 / 中くらい1.5 / 大きい・巨大1.0。仮の値）。星の数が少なくても、点でなく星として見せるため。
  - 既定の画角は、銀河の半径から **画角 = k × 半径^(−p)** で求める（p = 1 なら半径に反比例）。Home とページで同じ画角を使う。既定は k = 5.18、p = 1.16（巨大で3、生まれたてで15。段階ごとに 15 / 11.6 / 7.8 / 5.2 / 3.0）。開発者が画面で調整中。ピンチで引ける限界・寄れる限界も既定の画角に比例させる（既定の0.25倍〜2倍。以前の Home の既定4で1〜8と同じ比率。生まれたてで 3.7〜30、巨大で 0.75〜6）。星の大きさ・明るさの基準の範囲は1〜8のまま。
- 各段階に届く「集めた星の合計」は、**想定する1日の獲得数 × 到達させたい日数**（小さい7日 / 中くらい27日 / 大きい365日 / 巨大900日）で決める。
  - 想定する1日の獲得数は **約20個**（2026-11-22 の暫定の目安。開発者が実際にこの使い方をして見直す）。講義: 1トピック1個 × 1講義平均4.5トピック × 1日平均1〜1.5講義 ＝ 5〜6個。チャット: 1回20〜30個 × 2日に1回 ＝ 10〜15個。
  - 1日20個なら各段階は 0 / 140 / 540 / 7,300 / 18,000 個。
- 「1年で2万個」は、獲得する星ではなく銀河の見た目（描画する星）の目標。

### 3. Stats の数字と気持ちよさ
- Stats には **集めた星の数**（と、授業トピックの数・チャットの数・自分を発見できた数など）を出す。
- 数字の気持ちよさは絶対的な大きさではなく相対的なもの。1回で0.2しか上がらないなら100はすごい数字になる。意味のあるものだけを数えるので、数百・数千と溜まっていくこと自体が気持ちのいい体験になる。
- 使う頻度によって育つ速さが違うのは良いこと。早く育つのを見たいからたくさん使う。星の数や銀河の大きさは、その人のステータスになる。

## 星の抽出・生成設計（現行機能からのパイプライン）

初期フェーズ（MVP）では、**「①講義内容」** と **「②AIチャット」** の2つを星の源泉とし、既存のデータ・推論パイプラインを最大限に活用する。

### 1. 講義からの抽出（DAG Phase 6 並行アセンブル）
- **DAG配置**: `REVIEW_CARD_GENERATION` の直後（Phase 6 並行タスク群内、`GALAXY_STARS_GENERATION`）。
- **依存関係**: `dependencies: ["REVIEW_CARD_GENERATION"]` （FINALIZE_JOBより前）。
- **データ源（すべて生成済みの資産を活用）**:
  - `CORE_EXTRACTION`: トピックタイトル（大星候補）、トピック要約、キーワード（定義付き、各3〜6個）。
  - `REVIEW_CARD_GENERATION`: `micro_topics`（各3〜5個、タイトル＋要約）、`gotcha`（要点・Aha体験）。
- **抽出・アセンブル内容**（※2026-11-22 最終決定: 獲得する星はトピックの数だけ。下の子星は大星の中身として持つが、星の数には数えない）:
  - **大星（3〜5個）**: 各トピックの核心コンセプト。
  - **子星（各トピック10〜15個）**:
    - キーワード群（定義付き）: 3〜6個
    - MicroTopics群: 3〜5個
    - Gotcha / Hook の要点: 2〜4個
- **メリット**: **追加のLLMコストほぼゼロ・超高速**。すでに高精度に生成されたテキストを整形して `galaxy_stars` にINSERTするだけで完了。

### 2. AIチャットからの抽出（2026-11-22 決定: 案2 を「根拠1つ＝星1個」で採用。案1 は不採用）

チャットの星を講義より多くしたい理由（説明 #12）: 講義は受講が必要だから録音しているもので、学びがなくても星になる。チャットは「こう思った」「これをしてみたい」「なぜだろう」のように本人の内面から出てくる内容なので、自分らしさの銀河にはチャットの内容を多く詰め込みたい。講義の星とチャットの星は重複しない前提。

実データ（2026-11-21 集計、全61スレッド・1,088メッセージ。母数が少なく、開発者本人の利用が中心と思われる）:
- 1スレッドのユーザー往復数: 中央値 4、上位10%で 27
- 1スレッドのユーザー発言の合計文字数: 中央値 204、上位25%で 1,512、上位10%で 3,752
- → ユーザーの発言から「中身のある星」だけを100〜200個抽出するのは難しい。

#### 案1: 対話の事実構造から分解 ＋ スターパワー（光の粒子）
- **リアルタイムUX**:
  - 会話終了後の受動的な通知ではなく、**AI回答が返ってきた瞬間にキラキラと星が生まれ、銀河へ飛んでいく演出**をリアルタイム表示。
- **判定と非同期実行**:
  - `Chat Router` に `has_star_spark`（ユーザーの気づき・熱量・深い学びの有無）判定フラグを追加。
  - `has_star_spark == true` の時だけ、AI回答ストリーミングの裏で軽量な星抽出タスクを実行し、回答完了と同時に星イベントを返却。
- **星の真実性（ゼロハルシネーションの徹底）**:
  - AIによる勝手な性格診断や推測の心理分析、中身のないダミー空星は**一切生成しない**。
  - **対話の事実構造から5つの要素を星として分解（1対話あたり10〜20星）**:
    1. `問いの星 (Question)`: ユーザーが抱いた疑問やモヤモヤ（例:「なぜ関数型は状態を持たないのか？」）
    2. `気づきの星 (Insight)`: 対話の中で「なるほど！」となった核心（例:「副作用を境界外に追いやるため」）
    3. `実体験の星 (Experience)`: ユーザーが語った具体例（例:「Reduxで状態管理がカオスになった経験」）
    4. `概念の星 (Key Concept)`: 会話に登場した重要用語（例:「純粋関数」「イミュータビリティ」）
    5. `好奇心の星 (Curiosity)`: 会話から生まれた次の関心（例:「Rustの並行処理も見てみたい」）
- **「100スター獲得」との両立（スターパワー / 光の粒子）**:
  - 図鑑に登録される星レコードは上記の本物（10〜20個）。
  - 銀河全体のビジュアル成長（Stats）としては、対話の深さに応じて **「+100〜300 スターパワー（光の粒子）」** を銀河の腕に注入。
  - これにより、空っぽの星で水増しすることなく、クエスト達成時の大量星ボーナスと銀河の急成長を完全両立する。
- **懸念（2026-11-21 Claude の指摘）**:
  - スターパワーは「中身のない星」を別名にしただけで、星と粒子という2つの単位ができる。「+100スター」が実は「+100粒子」だと気づかれると、避けたかった水増しと同じ印象になる。
  - 「1対話10〜20星」という数を先に決めて5分類で埋めるため、短いチャットほど水増しになる。「概念の星」は講義キーワード由来の星と重複しやすい。

#### 案2: 名前のある星＋根拠の数だけ生まれる名前のない星（2026-11-22 更新）
- **考え方**:
  - 実際の夜空でも、名前のある星はごく一部で、残りの無数の星も銀河を作っている（プレアデス星団は千個以上の星のうち、肉眼で見えて名前があるのは7つ程度）。
  - すべての星に中身を持たせるのはやめる。その代わり **すべての星は、どの授業・どの会話から生まれたかを持つ**。
  - 名前のない星1つは、「これは自分のことだ」と言える **根拠1つ** に対応する。スコアを星の数に変換するのではなく、数えられる事実を1つずつ星にする。名前はなくても、1つ1つに存在する理由がある。
  - 設計上は「名前のある星1つ＋その名前のない星たち」を星団と呼ぶ（内部用語。ユーザーには使わない）。
- **星の3段階**:

  | 段階 | 中身 | どこで見えるか |
  |---|---|---|
  | 名前のある星（主星） | 名前・説明・出典・本人の言葉 | 図鑑の一覧、星座・星雲の材料 |
  | 小星（`micro_stars`） | 短い名前と説明 | 名前のある星を開いたときに並ぶ |
  | 名前のない星 | 出典と根拠の種類だけ（数のみ） | 銀河の見た目と数字、名前のある星の内訳 |

- **名前のない星になる5種類の根拠**:

  | 種類 | 数えるもの | 表すもの |
  |---|---|---|
  | 自分の言葉 | そのテーマについて、AIに聞かれる前に自分から話した発言 | 自分らしさ |
  | 心が動いた | 強い反応が出た発言 | 自分らしさ |
  | 経験 | 本人が語った具体的な実体験 | 自分らしさ |
  | 未来とのつながり | 将来の目標・興味と意味的に近い | 未来のためになっている度合い |
  | 過去の自分とのつながり | **別の日に**同じテーマへ戻ってきた回数 | 一時的ではない本当の関心 |

  - 材料は既存の自己像パイプラインを使える（migration `20261007000000_add_self_portrait_profile.sql`）: `profile_observations` の `initiative`（user / ai）、`reaction`（strong〜neutral）、`kind_hint`（`future`・`record` など）、`quote`、`source_message_ids`。未来の基準は `user_profiles.future_goals` と `interests`。
  - `certainty` が `inferred`（AIの推測）のものは数えない。`stated` と `strong_implicit` だけ。
  - ~~年間2万個に合わせるため「根拠1つ＝星 k 個」の係数 k を種類ごとに持つ。~~ → 2026-11-22 最終決定で不要。根拠1つ＝星1個。年2万個は見た目（描画する星）の目標になった。
- **この方式の性質**:
  - **講義とチャットに同じ計算を使う**。講義の星には自分の言葉も心の動きもないので自然に少なくなり、チャットが多くなる。固定の倍率（チャットは2倍など）は要らない。ただし将来の目標につながる授業の星は多くなり、「今どの授業が一番重要か」がわかる。
  - **星は後からも増える**。別の日にテーマへ戻る、新しい目標を書く、などで昔の名前のある星に仲間が加わる（「3か月前の星に、今日12個の星が加わった」）。星の数は減らさない。
  - **偏りの抑え方**: 過去とのつながりは同じ日の繰り返しを数えず、別の日に戻ってきたことだけ数える。
  - **目標が空のユーザー**: `future_goals` が空なら `interests` や `kind_hint = future` の観察で代わりに測る。
- **見せ方**:
  - 単位は星の数。「50個の星が誕生しました（うち名前のある星 5）」。「星団」という言葉はユーザーに出さない。
  - Stats: 「銀河の星 20,000 ／ 名前のある星 1,040 ／ 星座 6」。
  - 名前のある星の詳細: 「この星の仲間 38個：自分の言葉 14・心が動いた 6・経験 3・未来とのつながり 9・過去とのつながり 6」。採点ではなく事実の数として見せる。根拠の種類ごとに名前のない星の色や光り方を変え、塊を見るだけで性格がわかるようにする案もある。
  - 図鑑: 名前のある星だけを並べる。名前のない星を個別に一覧に出さない。
  - 銀河View: チャットから生まれた星は腕の上の明るい塊（星形成領域）として見える。
  - 恒星View: 名前のある星の周りに名前のない星が小さく瞬く（太陽系のように回す見せ方も可）。
- **データモデルへの影響**:
  - 大星＋小星の親子構造はそのまま。
  - 名前のない星は根拠の種類ごとの数（例: `{"own_words": 14, "emotion": 6, "experience": 3, "future": 9, "revisit": 6}`）と、根拠の参照（メッセージID・目標・過去の星ID）を持つ。見た目は名前のある星の `visual_attributes` とシード値から描画時に作り、DBには保存しない。
- **リアルタイム処理**:
  - ルーターは「内面から出た発言か」だけを判定する（軽い判定）。
  - 星はその場で生み、名前・説明と根拠の数は裏で走るLLM抽出の完了時に埋める。

### 3. 将来拡張（ロードマップ）
- **自由セッション録音**: 講義に限らず、「思考の独り言・アイデア出し」「TAとのディスカッション（ザワザワしたQAやまとめ）」「特別セミナー・ゲスト講義」「スライドのみの読込」など、雑多に詰め込める自由度の高い録音機能。
- **日記・ライフログ機能**: 一方通行の手軽なテキスト/音声記録＋AIからの関心フォローアップ。

## データモデル（方針）

### 1. 「大星（親星）」と「小星（従属星群）」の親子構造
2万個の星を個別のDB行としてフラットに管理するのではなく、**「主要テーマを司る大星（親）」の中に「5〜20個の小星（子）」を内包する階層構造**を採用する。

### 2. Supabase テーブル定義ドラフト (`galaxy_stars`)

```sql
CREATE TABLE public.galaxy_stars (
    id uuid DEFAULT gen_random_uuid() NOT NULL PRIMARY KEY,
    user_id uuid NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
    
    -- 星の基本情報
    title text NOT NULL,                                -- 星の名前（象徴的コンセプト、例:「直交行列の幾何学的解釈」）
    description text DEFAULT ''::text NOT NULL,         -- 学び・気づき・ストーリーの要約
    kind text NOT NULL,                                 -- 種類: 'insight'(気づき), 'learning'(学び), 'emotion'(感情/思い), 'interest'(興味), 'experience'(経験)
    tags text[] DEFAULT '{}'::text[] NOT NULL,          -- 分野・カテゴリ・性格タグ（['software_engineering', 'math', 'philosophy'] など。星座・星雲の種）
    
    -- 出典・コンテキスト
    source_type text NOT NULL,                          -- 'lecture' | 'chat' | 'diary' | 'audio_memo'
    source_id uuid,                                     -- 元の lectures.id または chat_threads.id
    source_quote text,                                  -- 本人の生の声や講義の決定的な発言引用
    
    -- ビジュアル描画用パラメータ（恒星View・プロシージャル生成用）
    visual_attributes jsonb DEFAULT '{}'::jsonb NOT NULL,
    -- 例: { "spectral_type": "blue_giant", "color": "#38bdf8", "magnitude": 1.2, "pulsing": true }
    
    -- 小星群（子星リスト）
    micro_stars_count integer DEFAULT 0 NOT NULL,       -- 内包する小星の数（2026-11-22: 講義の小星は星の数に数えない。チャットの根拠の数の持ち方は実装時に決める）
    micro_stars jsonb DEFAULT '[]'::jsonb NOT NULL,     -- 子星リスト
    -- 例: [ { "name": "内積の不変性", "magnitude": 0.3, "created_at": "..." }, ... ]
    
    -- ベクトル埋め込み（星雲クラスタリング・星座判定用）
    embedding extensions.vector(768),
    embedding_model text,
    
    -- 拡張用メタデータ & ライフサイクル
    metadata jsonb DEFAULT '{}'::jsonb NOT NULL,        -- クエストIDや将来の拡張データ
    deleted_at timestamp with time zone,                -- 論理削除（ゴミ箱）
    created_at timestamp with time zone DEFAULT now() NOT NULL,
    updated_at timestamp with time zone DEFAULT now()
);

-- インデックス
CREATE INDEX idx_galaxy_stars_user_active ON public.galaxy_stars (user_id) WHERE deleted_at IS NULL;
CREATE INDEX idx_galaxy_stars_tags ON public.galaxy_stars USING gin (tags);
CREATE INDEX idx_galaxy_stars_source ON public.galaxy_stars (source_type, source_id);
-- ベクトルインデックス（コサイン距離検索）
CREATE INDEX idx_galaxy_stars_embedding ON public.galaxy_stars 
    USING hnsw (embedding extensions.vector_cosine_ops)
    WHERE deleted_at IS NULL;
```

#### この設計のポイントとベクトルの保存先
- **ベクトルの保存先**: `knowledge_chunks` ではなく **`galaxy_stars.embedding` に直接持たせる**。
  - 星座や星雲を計算する際の「意味の近い星を集めるコサイン類似度検索」が、`galaxy_stars` 単体で `ORDER BY embedding <=> target_vector` のように一撃で超高速実行できる。
  - チャットのRAG用知識チャンク（`knowledge_chunks`）と、ユーザーの自己対話・銀河の星という異なるドメインのデータが混ざらず、設計が極めてクリーンに保たれる。
- **子星（`micro_stars`）の持たせる情報**:
  - 親星と共通（継承）: `kind`, `tags`, `source_type`, `source_id`, `occurred_at`
  - 子星が個別にフル保持:
    ```json
    {
      "id": "ms_01",
      "title": "内積の不変性",
      "description": "直交変換によってベクトルの長さと角度が保たれる性質。基底を変えても幾何学的本質が変わらないことの美しさ。",
      "visual_attributes": {
        "color": "#7dd3fc",
        "magnitude": 0.45,
        "size": 0.8,
        "pulsing": false
      }
    }
    ```
  - **容量試算**: 1子星あたり約300〜400バイト。15個の子星が入っても1行あたり約5〜6KB程度。1年分（大星1,000件）でも全体でわずか5〜6MB程度であり、DB負荷は極めて安全。
  - **描画効果**: これにより、銀河や星雲の中で「同じ親から生まれた星たち」であっても、一粒一粒が微妙に異なる色・光・大きさでキラキラと輝き、見た目の豊かさとタップしたときの図鑑体験が劇的に向上する。

## 銀河の成長ペースとバイアス制御

### 1. 1年20,000星のプログレッション曲線（数式による連続成長）

> 2026-11-22 最終決定で置き換え（冒頭の「星の数え方と銀河の成長」を参照）。以下は経緯として残す。獲得ペースの数字（1講義30〜80星、チャット最大500星、1日100〜300星）はもう使わない。

- **初期状態 (Day 1)**: バルジ（中心核）のみの小さな銀河（`diskStarCount: 0` 付近）。
- **獲得ペース**:
  - 1講義の分析: 大星 2〜4個 ＋ 小星群 ＝ **合計 30〜80星**
  - 密度の濃いチャット/日記: 大星 5〜10個 ＋ 小星群 ＝ **最大 300〜500星**
  - アプリ利用日平均: **1日 100〜300星** が蓄積され、約1年で大銀河（20,000星・太い腕・多彩な星雲）へ成熟する。
- **数式による連続成長アプローチ**:
  - 離散的な切り替えではなく、星の総数 $N$ から滑らかに各パラメータを導出する関数を定義する。
  - **初期（0〜1,000星）の急成長**: 対数カーブ等を用い、最初の数百〜千個の間に銀河半径（`radius`）が急速に広がり、腕（`diskStarCount`）が一気に芽生える演出。
  - **成熟期（1,000〜20,000星）**: 半径拡大は緩やかになり、星々の密集度・腕の厚み・星雲の量（`nebulaCount`）がじっくりと深まる。

### 2. レベル制による機能・体験アンロック
数式による連続的なビジュアル成長に加え、マイルストーンとしての「Level」を設け、機能やカスタマイズを解放する：
- **Level 1（銀河誕生期）**: 星が急激に増えていく様子をダイナミックに楽しむ初期エフェクト期。
- **Level 2（カスタマイズ解放期）**: 中心核の発光色（Core Gradient）や星雲の色味を自分好みに改造・調整できる機能がアンロック（※初期値はランダム割当、専攻固定ではなくユーザーの好みを尊重）。
- **Level 3以降（星座・星雲解放期）**: 蓄積された大星たちから、AIによる「星座」「星雲」の生成・鑑賞Viewがアンロック。

### 3. パラメータの安全性ガード（形状破壊の防止）
- `bulgeRadiusNorm` や `innerDiskHoleNorm` など、極端にいじると銀河の幾何学形状が破綻・不自然になるパラメータは、固定値または安全域（Safe Bounds）内でのみ微調整する。
- Flutter実機およびWebappの双画面で視覚的に検証しながら調整する。

### 4. 話題バイアスの制御（話題テンプレート / クエスト方式）
- **課題**: 特定のトピックについて1日で熱狂的に長文チャットをした場合、そのトピックだけに星が過剰集中し、銀河全体のバランスが崩れる。
- **解決策**:
  - 単一スレッドでの星獲得に一定の減衰（上限キャップ）を設ける。
  - **話題テンプレート（クエスト）**: 「将来のキャリアの価値観について話してみよう」「最近面白かった課外活動は？」といった多様な切り口のプロンプト・問いかけを用意し、多角的な星を獲得することで銀河の偏りを自然に中和・調和させる。
