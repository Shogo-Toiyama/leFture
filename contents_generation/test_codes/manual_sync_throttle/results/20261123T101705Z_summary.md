# Manual store sync throttled by the summary reconcile (2026-11-23)

## Problem (seen in Sandbox)
- A new account signed up on a device whose Sandbox Apple ID already had an active Max subscription.
- At signup, `/billing/summary` ran the reconcile and took the shared DB slot (`claim_store_sync_slot`). RevenueCat had no subscription for the new user yet.
- About 20 s later, `syncPurchases` after login caused a RevenueCat `TRANSFER` to the new user. The backend TRANSFER handler found no source subscription (the source account had been deleted), so it did nothing.
- The app then called `/billing/sync-store-subscription`. It used the same DB slot with a 30 s interval, so it returned `throttled` and did nothing.
- Result: RevenueCat had Max for the user, the DB had no plan, until the next summary reconcile (6 h). "Restore Purchases" more than 30 s later fixed it (`RECONCILE_GRANT`, `missing_plan`).

## Change
- `store_reconcile.reconcile_user(..., use_db_slot=False)`: the manual sync no longer uses the shared DB slot. It is throttled per instance (30 s, `_LOCAL_MANUAL_CHECKED_AT`). Grants stay idempotent by `event_id`.
- `main.py` `/billing/sync-store-subscription` passes `use_db_slot=False`. Summary and patrol are unchanged.

## Test (`run_test.py`)
Runs the production `reconcile_user()` with a fake DB and fake RevenueCat. Plan definitions are read from production `subscription_plans` (read-only).

| Case | Expected | Result |
|---|---|---|
| A. Old call: summary at signup, manual 20 s later after TRANSFER | manual `throttled`, no plan in DB (bug reproduced) | pass |
| B. New call, same sequence | manual `grant` / `missing_plan`, Max in DB | pass |
| C. Manual 3 times at 0 s, 5 s, 31 s | run, `throttled`, run | pass |
| D. Manual, then summary, then summary 60 s later | manual does not use the summary slot; second summary `throttled` | pass |

- Writes to production: 0. External API calls: 0. Cost: $0.
- Latency per `reconcile_user()` call with fakes: under 1 ms (not representative of production, where the RevenueCat API call dominates).
