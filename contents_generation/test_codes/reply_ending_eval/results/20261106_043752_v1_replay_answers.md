**不変データ構造**は、一度作ったら中身を変えられないデータ構造のことです！📦🔒

---

## なぜ「変えられない」と便利なの？

データが変わらないと、**「今の値が途中で書き換わる」心配がなくなります**。だから、

- 複数のスレッドが同時に読んでも衝突しない（スレッドセーフ）
- 「いつ・どこで値が変わったか」を追いかけなくていい（デバッグしやすい）

という大きな利点があります。

---

## 「変更」はどうやるの？

変えられない代わりに、**変更した新しいバージョンを作ります**。ここで活躍するのが**構造共有**（structural sharing）です。変わらない部分は、元のデータとそのまま共有します。

```
元のリスト:    A → B → C
                 
新しいリスト:  X → [A → B → C を共有]
```

先頭に X を足すとき、A・B・C を全部コピーし直す必要はありません。新しく作るのは X だけで、残りは元のリストを指し示すだけです。これが「効率的に更新できる」ポイントなんです！✨

---

ちなみに、Review Cards の説明にあった「連結リストの末尾に追加すると遅い」というのは、末尾まで辿ってすべてのノードを作り直す必要があるケースの話です。構造共有の仕組みと合わせると、「どこをどう変えるか」で効率が大きく変わるのが見えてきますよ！🌳


## 型昇格（type promotion）とは？

**型昇格**は、**狭い型を広い型に変えて、値を失わずに扱える**ようにする仕組みです。前に出てきた「強制（coercion）」の一種で、コンパイラが自動でやってくれます。

たとえるなら、**小さいコップの水をバケツに移す**ようなものです。バケツに入れても水はこぼれません 🪣💧

```
  int（小さいコップ）  ──昇格──▶  double（大きいバケツ）
        5             ──────────▶     5.0   ✅ 何も失われない！
```

---

## 例でみてみよう 🧪

```cpp
int i = 5;
double d = 3.14;
std::cout << i + d;   // i は double に昇格してから足される
```

`i + d` の計算の前に、コンパイラが `i` を `double` に変えてくれます。そのため、計算は `double` どうしで行われます。`double` はすべての `int` の値を持てるので、この変換は安全です。

---

## どの型に昇格するか：優先順位で決まる 🎯

C++では、上から順にルールを確認して、最初に当てはまったものが変換先になります。

1. どちらかが `long double` なら、もう片方を `long double` に
2. そうでなく、どちらかが `double` なら、もう片方を `double` に
3. そうでなく、どちらかが `float` なら、もう片方を `float` に

`i + d` では、2番目のルールが当てはまるので、`i` が `double` になります。

---

## 強制との関係 👨‍👩‍👧

昇格は、強制という家族の中の一人です。

```
強制（自動の型変換）
 ├─ 昇格 🌱   狭い → 広い、値が失われない（int → double）
 └─ 縮小 ⚠️   情報が失われることがある（int → bool）
```

つまり、**すべての強制が昇格ではありません**。たとえば `int a = 5` を `if (a)` で使うと、`int` から `bool` への強制は起きますが、値が失われる縮小なので、昇格ではありません。

---

## テストのためのポイント 📝

- **昇格**：自動で行われ、狭い型から広い型へ。値は失われない
- **強制**：自動の型変換全般。情報が失われることもある
- 授業の定番例は `int → double` です。`double` はすべての `int` を持てるからですね
- `int → float` は、`float` がすべての `int` を正確に持てないので、きれいな昇格の例にはなりません

---

## なぜ別の型になるの？🤔

Go では、**名前が違う型は、中身が同じでも別の型**として扱われます。

```go
type Feline struct{ Name string }
type Cat struct{ Name string }

var f Feline = Feline{Name: "Tama"}
var c Cat = f        // ❌ コンパイルエラー：Feline を Cat として代入できない
var c2 Cat = Cat(f)  // ✅ 明示的に変換すれば OK
```

`Cat(f)` のような**明示的な変換**が必要なのがポイントです。サブタイプなら自動で代入できるはずなので、ここで「親子じゃない」と分かります。

## 答えを強くするひと言 ✨

## 結論：No で合ってる！🙆‍♀️

FelineもCatも**名前のある struct（名前付きの型）**なので、Go ではそれぞれ**別の型**として扱われます。名前が違うと、中身が似ていても親子の関係にはなりません。

```
Feline（struct）  ──── 親子の矢印 ❌ ────  Cat（struct）
   名前が違う → 別の型 🆚
   継承の宣言もない → 親子にならない
```

## 中身が同じでも「そのままは代入できない」💡

Go では、フィールドが全く同じ2つの struct でも、名前が違えば代入はそのままできません。ただし、**明示的な変換**をすれば使えます。

```go
var f Feline = Feline{Name: "Tama"}
var c Cat = Cat(f)   // OK：中身が同じなら明示的に変換できる ✅
// var c Cat = f     // NG：名前が違うので、そのままの代入はエラー ❌
```

つまり「**親子として自動で置き換えられる（サブタイプ）**」わけではなく、「**手動で変換して別の型に作り直す**」イメージです。
