## Findings
- System audio from the Zoom desktop app is captured while the user wears earphones (wired and Bluetooth).
- Chrome records AAC in MP4 (`audio/mp4;codecs=mp4a.40.2`) on this machine, i.e. `.m4a`.
- With Bluetooth earphones during a Zoom meeting, the output device ran at 16 kHz (hands-free mode) in both
  runs, including the muted one, and the captured audio lost almost everything above ~8 kHz
  (-40 to -50 dB vs -24 dB wired). 4–7.5 kHz content is kept, so it is 16 kHz-equivalent audio, not narrowband.
- `decoded.sampleRate` in the run JSON is the page AudioContext's rate (= current output device rate),
  not the file's rate; the m4a files store 48 kHz (mdhd timescale).

## Mic recording vs. macOS sleep (mic_probe.html, 2026-11-08, $0)
Chrome 156 started with a fake mic (`--use-fake-device-for-media-stream`), MediaRecorder confirmed recording
(chunks of ~105 KB / 10 s in results/mic_probe_*.json), then `pmset -g assertions` at 15 s:

| page | Chrome's power assertions |
|---|---|
| mic recording only | none (only a transient "Download in progress" from the fresh profile) |
| mic recording + `navigator.wakeLock.request('screen')` | `NoDisplaySleepAssertion "Blink Wake Lock"` |

- Recording by itself does not keep the Mac awake. A screen wake lock keeps the display on, and powerd then
  holds "Prevent sleep while display is on", so the system stays awake.
- The wake lock is dropped when the tab is hidden (seen in the 62-min run), so it only helps while the
  leFture tab is in front.
- This Mac's timers: battery displaysleep 2 min / AC 10 min, then system sleep 1 min later.

## MediaRecorder pause/resume with AAC-in-MP4 (pause_probe.html, 2026-11-08, $0)
Headless Chrome 156, fake mic, 64 kbps / 10 s slices: record 6 s -> pause 6 s -> record 6 s -> stop.
- One file; browser decode 11.99 s, ffprobe (4.4 / 5.1 / 7.1) 11.986 s, full decode 11.98 s.
  The paused time is excluded, so the file holds only the recorded parts and the backend reads it unchanged.
- No dataavailable fires while paused; the 10 s timeslice counts recorded time (first chunk at wall 16.5 s).

## Can a page see the macOS screen-recording permission in advance? (permission_probe.html, 2026-11-09, $0)
Chrome 156 on this Mac, where Chrome already has the macOS permission (the user recorded successfully):
`navigator.permissions.query` -> display-capture "prompt", microphone "prompt", camera "prompt".
- "display-capture" is the per-site prompt state, not the macOS setting, so it cannot tell whether
  System Settings allows Chrome. No web API exposes that; the page only learns it when getDisplayMedia() fails.
- Not verified yet: the exact error Chrome 156 returns when macOS blocks it (the code assumes a message
  containing "system", e.g. "Permission denied by system"). Needs one run with the permission turned off.

## First run on a Mac with Chrome's permission off (denied_probe.html + user's screenshots, 2026-11-08 22:31–22:32, $0)
macOS 27.2 (English UI), Chrome 156. What the user went through, in order:
1. Chrome's picker opens normally (getDisplayMedia did not reject). The "Entire Screen" pane says
   "To share your screen, allow screen recording for Chrome in System Settings. You'll then need to restart
   Chrome." with an "Open System Settings" button. On top, macOS asks: "Google Chrome would like to record this
   computer's screen and audio." [Open System Settings] [Deny].
2. System Settings > Privacy & Security > "Screen & System Audio Recording": turn on Google Chrome.
   (A separate "System Audio Recording Only" list exists below; Chrome was not in it.)
3. macOS: "Google Chrome may not be able to record the contents of your screen until it is quit."
   [Quit & Reopen] [Later].
4. After reopening and starting again: "Google Chrome is requesting to bypass the system private window picker
   and directly access your screen and audio." [Allow] [Open System Settings] (shown twice in the screenshot).
5. "Google Chrome would like access to record your system audio. Once Chrome has access, websites will be able
   to ask you for access." [Don't Allow] [Allow].
- The saved run (after reopening) was `outcome: granted`, System Audio track, 13.7 s from click to share.
- The permission-off attempt itself was not saved (Chrome quit through "Quit & Reopen" before the page finished),
  so the error a page gets when the user clicks Cancel/Deny there is still unknown.
- Chrome and macOS already explain the missing permission inside the picker; a page never sees a rejection while
  the user is in that flow. The page's own job is to set expectations (about five prompts, one Chrome restart,
  press Start again after the restart).
