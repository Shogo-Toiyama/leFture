# Web Review Cards scroll and bracket emphasis

Run `node contents_generation/test_codes/web_review_card_parity/run.mjs`
from the repository root. The harness bundles the production viewer,
navigation, annotation renderer, and Markdown pipeline with synthetic fixture
data, then runs local HTML in headless Chromium. The test uses touch pointer
events. No production rows or remote API calls were used.

| Check | Before | After |
| --- | --- | --- |
| First card before swipe → departure → revisit | 230 → 0 → 0 px | 230 → 230 → 230 px |
| Second card first visit → departure → revisit | 0 → 0 → 0 px | 0 → 120 → 120 px |
| Bracketed emphasis beside Japanese prose | Markers appeared as text | Bracketed content rendered inside `strong` |
| Highlight with offsets based on Markdown-free text | Began on the literal asterisks | Covered the intended term |
| Code, escaped markers, and math | Passed | Passed |

The installed Markdown renderer already treated the isolated
`**サンク(thunk)**` as strong emphasis. Adding `を使う` immediately after it
reproduced the missing emphasis. The bracket attention extension keeps
parentheses inside the strong span and handles consecutive emphasized spans
without changing the Markdown string. It is enabled in the shared Review Cards
and Deep Notes renderer and the Review Cards code-block explanations.

All four Chromium browser checks passed in the final fixture run, which took
1,797 ms including bundling and browser startup. The production build
(`tsc && vite build`) passed, with Vite reporting 4.46 s. These timings do
not measure interactive rendering. External API cost and LLM usage were zero.
Physical phones and Safari were not tested. No stored annotation offsets were
migrated. A Web annotation saved while the asterisks were visible may still
refer to the earlier character offsets.
