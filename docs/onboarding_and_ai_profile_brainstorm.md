# オンボーディング & AIプロフィール ブレインストーミング (2026-07-05)

## 背景・課題

フロントエンドにSupabaseの実データを繋ぎ込む作業（HomePage / CoursePage / LectureViewerPage）の前段として、「コンテンツが何もない時に何を表示するか」を検討した。

一番の問題はHomePage: コースが0件のとき、以下の理由でほぼ何も表示するものがない。

- `AnnouncementBar`: 固定のダミーテキスト
- `FunFactsCarousel`: ダミー5件固定
- `RecentLecturesList`: ダミー10件固定
- 銀河ビュー(`GalaxyView`)は将来「学習するにつれ星が増えて成長する」仕様にする予定なので、初回は星0個の状態が正しい

## 方向性: 空状態のホームページ

検討した案：

- **A. 銀河の起源ストーリー演出**（採用したい方向）
  空の銀河を「まだ何もない寂しい状態」ではなく「これから生まれる場所」として演出。中心に控えめな光の粒（プロトスター）を置き、「最初の星を灯そう」のようなコピー＋録音導線を添える。銀河の成長メタファーをオンボーディングの瞬間から使い始める。
- B. 簡易オンボーディング質問（タグ選択等、AIチャット無しの代替） — 将来Cと統合できると良い
- C. チェックリスト/ロードマップ型オンボーディング（「①興味を教えてください→②最初の授業を録音→③FunFactを見る」）
- D. シンプルなCTA一本（「録音してください」）— 実装は最小だが機会損失が大きい

→ **A + 将来的にB/Cの要素を混ぜる方向**で合意。まずはAをUI実装の対象にする。

## AIプロフィールチャット構想

このアプリの核は「学習者にパーソナライズされ最適化していくこと」。将来的には、オンボーディングでAIと会話しながら興味・将来の目標を深掘りし、それが授業分析・FunFact生成のパーソナライズ元になる。

### 現時点でのRAG要否の整理

- **プロフィール構築チャット自体にはRAGは不要**。会話全体がコンテキストウィンドウに収まり、検索すべき既存知識も少ないため、system promptに直接注入すれば足りる。
- **RAGが必要になるのは「過去の講義内容を横断的に参照しながら会話する」機能**（例:「先週のあの授業の話をもう一度」「量子力学と先週の生物学の繋がりは？」）。講義数が増えるほど全部をcontextに詰め込めなくなるタイミングで必要になる。

### 今のうちにやっておくべきこと（保険としてのEmbedding）

- 講義の`core_extraction`結果を保存するタイミングで、ついでにEmbeddingを計算しpgvectorカラムに保存しておく。
- プロフィール関連の会話も、要約確定時にEmbeddingを計算して保存しておく。
- 理由: 後からRAGを作る際の「既存データ全部への一括バックフィル」が面倒（レート制限・コスト・コード書き直し）なため、書き込み時に1回計算しておく方が圧倒的に安い。
- ただし**検索ロジック（類似検索→プロンプト注入）自体は今は作らない**。講義データがある程度溜まってから着手すれば良い。

### プロフィールのデータ設計

ユーザーが会話するたびに、会話内容そのものだけでなく、そこから垣間見える性格・興味・得意なこと・価値観などを抽出し、蓄積していく。ユーザーに見せる「プロフィール欄」やFunFacts生成に使う「プロフィール」は、これらの蓄積を要約したものになる。

設計方針：

1. **1段落の塊ではなく、カテゴリ別の小さな「insight」単位で保存する**
   - 理由: FunFacts生成時に「今回の講義テーマに関連する興味insightだけを検索して注入する」といった部分的な取り出しがしたくなるはず。
   - ユーザーに見せる「プロフィール欄」は、複数insightをLLMで1段落に要約し直した"表示用ビュー"として都度生成する。生データ（insight群）と表示要約は分離しておく。

   想定スキーマ（例）:
   ```
   profile_insights
     id, user_id, category (personality/interest/strength/belief/...),
     content (1-2文), embedding, confidence,
     source_thread_id, created_at, superseded_by (nullable)
   ```

2. **抽出タイミングは「会話スレッド終了ごと」を基本にする**
   - 10ターンごとの機械的な区切りより、会話の切れ目の方が文脈的にまとまりがありLLM抽出の精度が高い。
   - 長時間の会話の場合は10ターンごとの中間スナップショットも保険として持つのはアリ。

3. **矛盾・更新の扱いが一番重要な設計ポイント**
   - 単純追記だとユーザーの変化（例:「昔は初心者だったが今は詳しい」）に追従できず、古い情報がノイズとして蓄積する。
   - 新しいinsight保存前に、embeddingで類似検索し既存insightと突き合わせ、LLMに「強化/更新/矛盾」のどれかを判定させ、`superseded_by`で古いものを論理的に無効化する一手間を入れる。

4. **confidenceフィールド**
   - 本人が明言した情報か、会話から推測した情報かで信頼度が異なるため保持しておく。
   - 後のプロフィール要約・FunFacts生成で確度の高い情報を優先する重み付けに使える。

### まとめ

- insight単位での粒度保存 + embedding + カテゴリタグ + 矛盾解消ロジック、が肝。
- これがそのまま将来のRAG基盤にもなり、「表示用プロフィール」はその上に被せる要約ビューという位置づけ。
